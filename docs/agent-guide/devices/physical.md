# Working with Physical Devices

*`quern://guide/devices/physical` -- part of `quern://guide/devices` in the Quern agent guide. Start from `quern://guide`.*

Physical iOS devices are supported for screenshots, UI automation, log capture, and crash reports. On iOS 27 and later, quern drives an iPhone without WebDriverAgent (WDA) by default (below); before iOS 27, UI automation on a device uses WDA, which is built with Xcode, so those phones need Xcode installed. A simulator uses the accessibility tree (sim-bridge / idb) by default, and can be switched to WDA with `start_driver` — that is the way to see the element types XCUITest will see (`xcui_type`), and `stop_driver` switches it back.

**First-time setup (WDA only)**: Call `setup_wda` with the device UDID. This builds and installs WDA on the device, which requires a valid Apple Developer signing identity. If multiple identities exist, the tool returns a list — call again with the chosen `team_id`. The app appears on the device as **Quern Driver**.

**After setup**: WDA auto-starts the first time a call needs it: on an iPhone before iOS 27 or set to WDA, any interaction (screenshot, UI tree, tap, etc.); on iOS 27 and later, only a call that passes `snapshot_depth`, or any call once `start_driver` has been called for that phone (no-WDA mode, below). Before iOS 27 there is no need to call `start_driver` yourself: it happens transparently. The driver idles out after 15 minutes of inactivity.

**Screen reads without WDA (`backend: "coredevice"`)**: on iOS 27 and later, quern by default reads a physical iPhone's screen from the accessibility tree the device sends over its tunnel, instead of asking WDA. That covers `get_ui_tree` (`children_of` too) and `get_screen_summary` called without `snapshot_depth`, `strategy` or `mode`, at about 2 s a screen. Any of those asks for WDA's own read: it gets one where WDA can run, and otherwise fails naming why (see below). Element lookups (`tap_element`, `wait_for_element`, `get_element_state`) read the same tree, and so does the screen context in their answers. Passing `snapshot_depth` to any of them, or to `type_text` or `clear_text`, sends that call through WDA instead, so it needs WDA set up. Taps, swipes, buttons and typing go over CoreDevice HID; see below. The tree is what VoiceOver can reach, so it differs from WDA's in three ways:
- only elements on screen, and nothing hidden under a toolbar;
- a row's inner texts merged into one label ("Wi-Fi, Home" where WDA has a button and two texts);
- the element names a simulator uses (`CheckBox` for a switch, `Heading` for a title).

So a lookup by exact `label` also matches a row's title, the text before its first ", ": `label="Wi-Fi"` finds the "Wi-Fi, Home" row, and the answer says `matched_via: "merged_label"`. Only the title, not every part: "Home" does not find it. Prefer `identifier` for rows, which matches WDA's exactly. A miss is a miss as VoiceOver sees the screen -- an element off screen or under a toolbar is not there -- and the miss says so; `snapshot_depth` looks through WDA instead. A read it cannot make falls back to WDA, and `backend` on the answer says which one served it, with a `warning` saying why. After `stop_driver` on a phone the push reads (iOS 27 and later), WDA stays stopped: a read the push cannot make fails saying so instead of starting WDA again behind it, until `start_driver`. And a WDA runner found alive but not answering -- still working on something slow, such as a screen too busy for it -- is not asked again for 60 s: calls that would need it fail at once with a 503 naming it, where each used to wait on it in turn; `stop_driver` then `start_driver` resets it (#769). A screen with a great many elements -- a map with hundreds of pins, a very long list -- takes the phone longer to describe than a read allows: measured on an iPhone 12, a map with 26 elements read in 2.6 s, 128 in about 13 s, and 415 not within 45 s. One still being described at the deadline with 100 or more elements fails saying how many it has, and is not read through WDA, which cannot read it either; zoom a map in until 10-20 pins show, or filter or scroll a list, and read again (#769). A phone's push reads take turns, one connection at a time -- across every quern server the same user runs on the Mac, not only within one -- so calls made at once wait for each other rather than overlap. The wait counts against the call's own deadline: a read that ran out before its turn came says the phone was not asked, and is not read through WDA instead -- the push is busy, not broken, so ask again with more time -- and one whose turn came late says how long it waited. Overlapping connections failed about one read in seven and could wedge the phone's accessibility daemon, `axauditd`, until every new connection timed out (#734). quern now notices a wedge within 5 s and restarts the daemon, at most once a minute per server, and the answer's `warning` says so -- on `launch_app` too, when its check was the read that found it. A phone whose daemon cannot be restarted is not asked again for 30 s: calls to that server in that time fall back, or fail, at once. The same setting sends taps, long presses, swipes (edge swipes included), multi-finger gestures (pinch, rotate, two-finger pan, double and two-finger taps), Home and the volume buttons over CoreDevice HID instead of WDA, about 0.07 s a tap once connected. `tap_element` taps what it found this way, and `tap` says which delivered it in `input`. A screen turned from its native orientation, or anything HID cannot send, goes through WDA. `clear_text` finds its field in the push and clears it with keystrokes over HID: a tap, then Cmd+A and Backspace, so the app sees the edit. `launch_app` and `terminate_app` go through `devicectl`. A terminate finds the app by its running process, so it stops one started any way. A launch is confirmed when the push shows the app's process in front; with `env` the running app is restarted, and `restarted` is null because `devicectl` doesn't say whether one was running. The scrolling that `scroll_to_element`, `tap_element`'s search and its scroll into view do goes over HID too, reading each step from the push, unless the call passes `snapshot_depth` (#678). The drags are slower than WDA's, about 2.7 s for a full step, because a faster HID drag carries the list past the finger and could skip rows. Measured on an iPhone 11, `tap_element` found a row 150 rows down in 84 s with no WDA, about what the same sweep took through WDA. `type_text` goes over a virtual HID keyboard too, so the app sees real keystrokes and its editing callbacks run. The phone decodes them with its own keyboard and input method, which nothing reports: a Japanese keyboard turned "Hello abc #@" into "Helloあbc＃＠". So with a field named, quern reads it back. Text the keyboard changed (kana or full-width characters from ASCII keys), or that has a character no US key types, is set directly through the accessibility service. Any other mismatch, such as autocorrect, an input mask or a validator, still fails as it does through WDA, because setting the text would overwrite the app's own change. The answer then says `set_through_accessibility: true`, and the app's callbacks (input masks, formatters) did not run for that text. A password field is never set that way. Name the field: untargeted typing can't be checked or corrected. Measured on an iPhone 11, about 8.5 s a call, or 14 s when it has to correct; most of it is waiting for the screen to settle while the keyboard appears. An iOS 27 bug in UIKit's accessibility code makes the push read crash some apps: UIKit apps on a tab that is a navigation controller, reached through a tab bar's More list (#669). It is Apple's bug, not the app's or quern's. When it does, a lookup (`tap_element`, `wait_for_element`, `get_element_state`), `type_text`, `clear_text` or a scroll sweep fails, saying nothing was done, since the screen it was for is gone. A screen read's answer carries a `warning` naming the app. Where WDA can run, that read comes from WDA, and the device's screens are read through WDA until the server restarts. Where it cannot, the read is the push's of what the crash left, and the device stays on the push, so a read of that screen may crash the app again. A phone can also answer the push for every newly launched app with one unlabelled `Application`, while the home screen reads normally: a wedge in iOS, measured on an iPhone 15 Pro, that a restart of the phone clears (#664). After a second read a second later says the same, quern reads such a screen through WDA instead and says why: in a `warning` on a screen read and on a `tap_element` or `wait_for_element` miss, and in a lookup's not-found message. With no WDA to read it, the read or lookup fails naming the wedge, with WDA's own status, rather than finding nothing. A `not_exists` wait the push satisfies carries a `note`: text merged into a row is no element of its own there.

**Choosing the reader, and a Mac without WDA**: the owner can send everything back through WDA with `quern set-device-reader wda`, or the iPhone control setting in the menu-bar app's Settings; `quern set-device-reader no-wda` is the default again. Where `setup_wda` has not built WDA, quern never starts one: each place that would fall back to WDA fails instead, naming the reason, and after a #669 crash the device stays on the push with a `warning` rather than moving to WDA. A `wda` setting there behaves as no WDA. WDA is built and run with Xcode, so an iPhone before iOS 27 needs it; one on iOS 27 or later is driven without it (see below). With no Xcode, quern says so instead of starting a WDA that cannot run, and WDA is not a choice: `quern set-device-reader wda` refuses, Settings greys it out, and a `wda` already set is set aside until Xcode is installed. `quern doctor` reports which one is in use and whether WDA can run.

**No-WDA mode (#780)**: on an iPhone on iOS 27 or later, quern does not start WebDriverAgent on its own. A read the push cannot make, or input HID cannot send, fails with that reason followed by "is in no-WDA mode", instead of starting a WDA nobody asked for. If the task really needs WDA, call `start_driver` for the device: WDA is then used for it, and started again when needed, until `stop_driver`. A call that passes `snapshot_depth` asks for WDA by itself. The owner can restore the automatic fallback for the whole Mac with `"wda_fallback": true` in `~/.quern/config.json`. `children_of` is answered from the push, which is flat: it returns the elements inside the parent's frame, and says so.

**An iPhone on Wi-Fi only (#781)**: quern's own tunnel daemon builds tunnels over USB alone. So for a phone that is paired with the Mac but not plugged in, quern rides the tunnel macOS keeps to it itself, the one Xcode and `devicectl` use. Screen reads, lookups, taps, swipes, typing, buttons and app launches then work as over USB, and `devicectl` keeps working beside them. A listed phone says `tunnel: "native"` while quern holds that tunnel, and quern gives it up a minute after the last call that used it. Measured on an iPhone 11 on iOS 27.2.1: the first call opened the tunnel in about 1 s, and a screen read took about 3 s. When the tunnel cannot be opened, the call fails with "no tunnel" and the reason: at once for a phone devicectl doesn't list, and within 5 s for a listed one that can't be reached, remembered for 30 s. The phone must be paired with this Mac, unlocked, and on the same network.

**A Mac without Xcode (#706)**: an iPhone on iOS 27 or later is driven without it. `devicectl` comes with Xcode, so where there is none, quern lists the phone by its own UDID (`00008030-...`, the one Finder shows) and launches, stops and lists apps over the CoreDevice app service that `devicectl` uses, through pymobiledevice3: measured on an iPhone 11 with Xcode hidden, a launch was confirmed in 2.6 s and a terminate in 0.6 s. `launch_app`'s `env` still works. `install_app` installs a built, signed `.app` or `.ipa` through the phone's installation proxy (the probe app took 7 s); building and signing one is what needs Xcode, wherever that happens. `open_url` hands the URL to an app instead of the system's routing, which only WDA reaches: to `bundle_id` when given, otherwise an http(s) URL to Safari, where a universal link is not passed on to its app. Taps, typing, buttons and the app service need the developer disk image mounted; screen reads, screenshots and crash reports do not. A call that needs it and finds it missing mounts it first -- about 1 s, or 2 s when the image is downloaded -- and its answer says so in `developer_image`. If that mount fails, the call fails saying so. Xcode mounts it when it first meets a phone, and on iOS 27 it stays mounted across restarts; `quern doctor` reports it, with Developer Mode, for each iPhone on USB, and `quern doctor --fix` mounts a missing one with pymobiledevice3, which downloads Apple's image from its GitHub repository and has Apple's signing server personalize it for the phone. Without Xcode, some things cannot run, and say so instead of trying (#738): profiling (`xctrace`), `start_driver` and `setup_wda` (WebDriverAgent is built and run with `xcodebuild`), and symbolicating with `atos`, which leaves frames as addresses with the reason in each image's `note`.

**What works the same**: `take_screenshot`, `get_screen_summary`, `get_ui_tree`, `tap_element`, `swipe`, `type_text`, `wait_for_element`, `install_app`, `launch_app`, `terminate_app`.

**What's different**:
- `boot_device` / `shutdown_device` — simulators only
- `set_location` — simulators only
- `grant_permission` — simulators only
- `start_device_logging` / `stop_device_logging` — on-demand log capture for physical devices (vs `start_simulator_logging` for simulators). Captures os_log and Logger output only — `print()` writes to stdout and is not captured. Both support `preset` parameter to apply ingestion filters at start time
- `get_latest_crash` with a `udid` parameter — pulls crash reports directly from the physical device
- `tap_element` taps only an element a tap can reach: its centre on screen and XCUITest reporting it hittable. Elements read through WDA carry `on_screen`. When every match is unreachable the not-found response lists them and why — scroll the element into view (`scroll_to_element`) rather than retrying the tap
- Where WDA reads the screen (an iPhone before iOS 27, one set to WDA, a call passing `snapshot_depth`, or a simulator after `start_driver`), reads made for `tap_element`, `get_element_state`, `wait_for_element` and `scroll_to_element` go through it at depth 12, which keeps long lists fast (measured: 3.9s instead of 34.5s on a 200-row list). A miss looks once more at the full depth (25) -- bounded, and only when the first read was quick -- and that holds when you pass `snapshot_depth` too: the depth you give is a floor, not a ceiling. Pass `deepen: false` for a read at exactly that depth. Every miss reports how deep it looked
- A call that needs WDA (above) on a physical iPhone that has never had `setup_wda` is a **400 naming `setup_wda`**, not a failure to retry: run setup first
- `preview_device` — opens a live macOS video preview window of the device screen: CoreMediaIO for USB-connected physical devices, and quern-media's MJPEG stream for booted simulators. Each device is independently controlled — add and remove individual previews without affecting others. Use `stop_preview` with a UDID to close one device, or without to close all. `preview_status` shows per-device breakdown and what can be previewed, booted simulators included, each tagged `kind`. Asking again for a device already being previewed answers `already_active` with the original `started_at`: the stream is reused, not restarted. A simulator answer carries `on_air`, so a reused preview that is reattaching is not read as live
